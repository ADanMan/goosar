## 2. Что сделано по тикетам

**T-024.** Контракт `docs/50-api-contract.md` (правила, протоколы `/ws` и `/api/daemon/ws`, домены, приложения «CLI администратора» и «Переменные окружения сервера», 161 переменная) и OpenAPI 3.1 `docs/50-api-contract.yaml`. Спецификацию писали четыре агента-спецификатора по диапазонам маршрутизатора, интегратор собрал её и вычистил ссылки на исходники. Контрактные тесты лежат в `e2e/contract`: отдельный Go-модуль на kin-openapi, проверяет код ответа и схему тела. Правки контракта, найденные при сверке с эталоном, записаны в журнал `docs/50-api-contract-changes.md`. Скрипт `scripts/similarity-check.py` сравнивает `server2` со старым сервером.

**T-025.** Своя схема: `docs/51-data-model.md` и `server2/migrations`. У всех колонок есть префиксы таблиц, проверка имён — `server2/migrations/check_names.py`. Утилита `server2/cmd/import` переносит воркспейс через GET-операции контракта, сохраняет исходные uuid и идемпотентна. Проверил вручную: воркспейс с тремя задачами перенесён со старого сервера, пользователь входит в `server2` по тому же email, задачи на месте, новая задача получает номер 4. После этого полный контрактный прогон на той же БД прошёл.

**T-026.** Каркас `server2` на `net/http` ServeMux, pgx/v5, `coder/websocket` и собственном HMAC-JWT (обоснование — `server2/docs/adr/0001-stack.md`). Внутри: health/readiness, метрики, вход по коду, сессии, PAT, воркспейсы, авторизация по ролям. Все операции регистрируются из контракта генератором `tools/genstubs`. Переменные окружения сведены с приложением контракта в `server2/docs/env-parity.md`: 101 поддержана полностью, 19 частично, 41 читается и логируется как неподдерживаемая.

**T-027.** Задачи (фильтры, нумерация, дочерние задачи, таблица задач, автозапуск агента при назначении), комментарии, реакции, метки, свойства, вложения, закрепления, проекты, лента и настройки уведомлений, чат, очередь задач агентов, протокол `/ws` с подписками.

**T-028.** Daemon-протокол через REST и WS: claim через `SKIP LOCKED`, жизненный цикл задачи, токены агента. Также среды выполнения, агенты, отряды, навыки и их бандлы, шаблоны и конструктор агентов, дашборд, автопилоты (свой cron-планировщик с advisory lock, вебхуки с дайджестом токена), прокси облачных сред.

**T-029.** Администрирование деплоя: заявки deployment-admin с двумя каналами подтверждения, аудит, политика, MCP-серверы деплоя и воркспейса, конфиг, provisioning. Интеграции GitHub, GitLab/Gitea, Slack и Composio, биллинг-прокси, экспорт. Почта через Resend или SMTP, magic link, OIDC (своя проверка id_token), LDAP (свой BER-клиент), MFA TOTP с защитой от повторного кода, rate limiting. Единый пакет шифрования `internal/seal`. `server2/cmd/admin` (`goosar_admin`) повторяет все 10 команд эталонного CLI.

## 3. Как соблюдалась чистая комната

- Спецификаторы (T-024, T-025, приложение с env, сверка с эталоном) читали `server/`, `packages/core`, e2e и живой сервер. Реализаторы получали правила из промпта: «Не читай server/**. Пиши по спецификации»; им запрещено было открывать `server/**`, `packages/core/**`, файлы upstream-проекта и скрипты сверки маршрутов. Разрешены только `docs/50-*`, `docs/51-*`, `server2/**` и контрактные тесты.
- Каждый реализатор в отчёте подтвердил, что `server/**` и `packages/core/**` не открывал, и перечислил прочитанные файлы. Списки собраны в `server2/docs/decisions.md`.
- Старый сервер и CLI реализаторы видели только как чёрный ящик: HTTP на стенде `:8199`, бинарники `goosar` и `goosar_admin` (для последнего — только `--help`).
- Пробелы спецификации реализаторы не восполняли чтением кода. Они принимали решение сами и записывали его в `server2/docs/decisions.md`.

Ограничение метода: все роли исполняли агенты одной модели, разделённые промптами и отчётами. Техническая изоляция (отдельный checkout без `server/`) не применялась. По ТЗ проверка — по отчётам, ревью человеком всё равно нужно.

## 4. Что не сошлось с acceptance criteria

| Тикет | Критерий | Состояние |
|---|---|---|
| T-024 | Контрактный прогон против `v1.2.0` на стенде | Стенда нет. Прогон шёл против локально собранного текущего `main` (он и есть 1.2.0) на локальном Postgres 16: 0 расхождений. Docker в песочнице недоступен, поэтому testcontainers не использовались. |
| T-024 | Schemathesis | Не применялся (pip-зависимость). Вместо него свой Go-набор на kin-openapi; 41 операция из 406 не вызывается, в основном OAuth-колбэки и внешние интеграции. |
| T-025 | «e2e-прогон на перенесённых данных зелёный» | Зелёный контрактный прогон на БД после импорта. Playwright-прогон на перенесённых данных не делался, см. строку T-027. Не переносятся секреты, OAuth-токены, байты вложений, история ленты, чаты других участников, журнал очереди: контракт не даёт для них bulk-доступа (список в выводе импорта). |
| T-026 | Сходство ≥ 30% с исходным upstream-проектом | Сравнение шло только с `server/`: исходников upstream в песочнице нет, а `server/` — их производная. |
| T-027 | e2e фронта против `server2` без правок фронта | Частично. Вход, воркспейс и страница задач работают через Next dev-прокси на `server2`. Спеки `issues`/`issue-table`/`comments`/`navigation` падают в `e2e/helpers.ts`: хелпер ждёт кнопку «New Issue», а фронт после T-019/T-020 пишет «New Task». ## 5. Известные пробелы реализации

Подробности — `server2/docs/decisions.md` (разделы по тикетам) и `server2/docs/env-parity.md`. Главное:

- Не реализованы Redis-релей realtime (работает один инстанс; планировщик автопилотов от двойного запуска защищён), S3/CloudFront для вложений (только локальный диск), OCI-provisioning, экспорт метрик в формате Prometheus (свой JSON-экспорт), PostHog.
- Rate limiter хранит состояние в памяти процесса: при нескольких инстансах лимиты считаются на каждый инстанс отдельно.
- PR-карточки GitHub: поля checks_*/additions/deletions пустые, снапшот проверок не пересчитывается.
- Права вызова агента с целью `team` не поддержаны: нет домена команд.
- Каталоги шаблонов агентов и ролевых воркспейсов придуманы, в контракте их содержимого нет.
- Легаси-бутстрап онбординга на эталоне всегда отвечает 500. В контракте он описан как есть, `server2` отвечает штатно.
- `docs/50-api-contract.md`: `GOOSAR_DEPLOYMENT_PROFILE` по умолчанию даёт самый строгий профиль. При переключении это надо проверить на реальной конфигурации.

## 6. Как переключать (T-030, не выполнялось)

1. Ревью владельцем ветки `backend/clean-room`: `docs/50-*`, `docs/51-*`, `server2/docs/decisions.md`, `server2/docs/env-parity.md`.
2. Закрыть пробелы, которые блокируют прод: Redis-релей (если прод многоинстансный), S3, если вложения в прод-хранилище лежат в S3. Проверить `GOOSAR_DEPLOYMENT_PROFILE`/`ALLOWED_EMAIL*` на прод-конфиге.
3. Стенд: поднять `server2` (`go build -o server ./cmd/server`, `MIGRATE=true`) на пустой БД рядом со старым сервером. Для каждого воркспейса прода выполнить `server2/cmd/import --source-url <старый> --token <PAT владельца> --workspace <slug> --database-url <новая БД> --migrate`. Прогнать `e2e/contract` и Playwright против стенда, предварительно исправив в `e2e/helpers.ts` «New Issue» → «New Task». Подключить CLI-daemon и десктоп и выполнить задачу через Hermes.
4. Нагрузочное сравнение: список из 2000 задач, p95 `server2` не хуже `server/` более чем на 20%.
5. Секреты: выдать владельцам токенов новые PAT (хэши не переносятся), заново подключить OAuth-интеграции (GitHub App, Slack, Composio), заново ввести секреты агентов и MCP.
6. Прод: окно обслуживания. Старый сервер переводится в read-only, импорт, в `Dockerfile` и `docker-compose.selfhost*.yml` образ бэкенда переключается на сборку `server2` с теми же переменными окружения (см. `env-parity.md`). Откат — возврат образа и старой БД: она не изменяется, импорт только читает через API.
7. После недели стабильной работы: удалить `server/`, перегенерировать `packages/core/types` из `docs/50-api-contract.yaml`, повторить `license_audit.py` со ScanOSS, перевести ADR-0004 в Superseded новым ADR о бэкенде собственной реализации.
