# Изменения контракта по итогам сверки с эталоном (v1.2.0)

Документ фиксирует расхождения, найденные при прогоне расширенного
контрактного набора (`e2e/contract`) против запущенного эталонного сервера
v1.2.0, и то, как каждое было устранено. Реализатор server2 использует этот
список, чтобы синхронизировать поведение новой реализации со спецификацией:
раздел «Изменения спецификации» — это то, что должно измениться в server2
(если оно ещё этого не делает); раздел «Изменения тестов» — это правки самого
контрактного набора, не требующие никаких изменений в server2.

Все записи датированы 2026-09-28.

## Изменения спецификации (`docs/50-api-contract.yaml` / `.md`)

Каждое из следующих поведений подтверждено прямым обращением к эталону и
отражает то, что сервер реально делает сегодня — спецификация ранее этого
не документировала.

### 1. `POST /api/workspaces/{id}/vcs/connections` (`connectVcs`)

- **Было:** документированы только `200/400/502/503/401`.
- **Стало:** добавлен `404` — «VCS-интеграция выключена на этом деплое»,
  отдельно от `503` («интеграция не настроена, нет ключа шифрования»).
- **Почему:** это два разных условия отказа. `404` — фиче-флаг подключения
  self-hosted VCS выключен на деплое целиком (интеграция не предлагается
  вообще); `503` — флаг включён, но нет ключа для запечатывания секретов.
  Эталон при выключенном флаге отвечает `404`, а не `503` — этот путь просто
  не был описан.

### 2. `POST /api/me/onboarding/runtime-bootstrap` (`meBootstrapOnboardingWithRuntime`)

- **Было:** документированы только `200/400/403/401`.
- **Стало:** добавлен `500` с пояснением: легаси-путь, оставленный ради
  старых сборок десктоп-клиента; поведение заморожено и может отказывать на
  внутреннем состоянии, которое этот путь больше не учитывает (например, при
  создании встроенного агента-ассистента).
- **Почему:** прямой вызов с полностью корректным телом (существующие
  `workspace_id`/`runtime_id`, вызывающий — участник пространства) стабильно
  завершается на эталоне `500`. Это подтверждённое поведение
  заморожённого легаси-пути, а не что-то, что тест мог сделать иначе —
  значит, это должно быть в контракте, а не молчаливым сбоем валидации.

### 3. `GET /api/issues/{id}/pull-requests` (`listIssuePullRequests`)

- **Было:** тело ответа `200` — голый массив `IssuePullRequestLink[]`;
  сама схема `IssuePullRequestLink` содержала всего 6 полей
  (`issue_id`, `provider`, `url`, `number`, `title`, `state`), не
  соответствующих ни одному реальному полю ответа.
- **Стало:** тело ответа — объект `{"pull_requests": [...]}`. Схема элемента
  массива переписана полностью и теперь описывает реальный набор полей:
  `id`, `provider`, `workspace_id`, `repo_owner`, `repo_name`, `number`,
  `title`, `state`, `html_url`, `branch`, `author_login`,
  `author_avatar_url`, `merged_at`, `closed_at`, `pr_created_at`,
  `pr_updated_at`, `mergeable_state`, `mergeable`, `merge_state_status`,
  `snapshot_available`, `checks_rollup`, `checks_conclusion`,
  `checks_total`, `checks_passed`, `checks_failed`, `checks_running`,
  `checks_pending`, `failed_check_names`, `snapshot_stale`,
  `snapshot_fetched_at`, `additions`, `deletions`, `changed_files`.
- **Почему:** эталон всегда оборачивает список в объект с ключом
  `pull_requests` (используется общий формат ответа с GitHub App и
  self-hosted VCS pull request'ами), и элементы этого списка — это полные
  карточки pull request'а (статус проверок, метрики diff, снепшот из
  провайдера), а не урезанная связь issue↔PR. Старая схема не совпадала с
  реальным ответом ни по обёртке, ни по составу полей.

### 4. `AutopilotRun` (используется `triggerAutopilot`, `getAutopilotRun`, `listAutopilotRuns`)

- **Было:** поля `trigger_payload` и `result` были объявлены без `type` и
  без `nullable` — только текстовое описание.
- **Стало:** оба поля помечены `nullable: true` (с уточнением: `result` —
  `null`, пока запуск не завершён, либо если результата нет; `trigger_payload`
  — `null`, если для запуска нет сохранённого payload).
- **Почему:** оба поля — произвольный JSON, и эталон реально возвращает
  `null` для незавершённого запуска (`status=running`), например сразу
  после ручного триггера. Схема без явного `nullable` это запрещала.

### 5. `DELETE /api/skills/{id}/files/{fileId}` (`deleteSkillFile`)

- **Было:** документирован `200` с телом — пустым JSON-объектом.
- **Стало:** документирован `204` без тела.
- **Почему:** эталон отвечает `204 No Content` с пустым телом — это
  единообразно с остальными операциями удаления в контракте (`removeAgent`,
  `deleteWorkspace`, `deleteSkill` и т.д.), просто эта одна ручка была
  описана иначе по ошибке.

### 6. `POST /api/slack/binding/redeem` (`redeemSlackBindingToken`)

- **Было:** документированы только `200/400/403/409/410/401`.
- **Стало:** добавлен `503` — «Slack-интеграция не настроена на этом
  деплое».
- **Почему:** та же форма, что уже была принята для VCS/OIDC/LDAP —
  функциональность, требующая настройки на уровне деплоя, отвечает `503`,
  когда эта настройка отсутствует. Для этой конкретной ручки такой путь не
  был описан, хотя он документирован для соседних `slack/*` операций.

## Изменения тестов (`e2e/contract/*.go`, контракт не менялся)

### 1. `POST /api/auth/mfa/totp/enroll` — тест не учитывал уже документированный `503`

Тест жёстко требовал `200`, хотя контракт уже описывал `503` («второй
фактор нельзя сохранить — ключ шифрования не настроен») как штатный
альтернативный ответ для деплоя без этого ключа. Тест исправлен: при `503`
он логирует это как ожидаемый путь и пропускает остаток MFA-сценария
(подтверждение/повторный вход/восстановление/отключение), вместо того
чтобы валить весь набор.

### 2. Ни один запрос набора не отправлял заголовок платформы клиента

`POST /api/client-usage` по контракту обязателен к `web`/`desktop` в
заголовке платформы клиента и документированно отвечает `400`, если он не
`web`/`desktop`. HTTP-клиент тестового набора никогда не выставлял этот
заголовок ни на одном запросе, поэтому попадал в этот же `400` вместо
`204`. Клиент набора исправлен: теперь каждый запрос (обычный и
multipart) выставляет заголовок платформы в `web` — как это делает любой
реальный веб-клиент.

### 3. `POST /api/autopilots/{id}/collaborators` — второй пользователь не был участником пространства к моменту вызова

Контракт требует, чтобы `user_id` уже был участником пространства
(документированный `400` иначе). Общий «второй пользователь» тестового
набора действительно становится участником пространства в сценарии
`workspaces`, но там же и удаляется из участников — это часть проверки
жизненного цикла участников. К моменту сценария `autopilots` (который
выполняется позже и переиспользует того же пользователя) он уже не
участник. Тест исправлен: перед выдачей прав коллаборатора он заново
приглашает и подтверждает этого пользователя в то же пространство.

### 4. `PUT /api/agents/{id}/runtime-skills/enabled` — рантайм фикстуры не подходил по провайдеру

Контракт ограничивает эту операцию агентами на рантайме одного из двух
конкретных провайдеров, которые поставляют встроенные навыки рантайма;
общий рантайм тестовой фикстуры — не из их числа, поэтому вызов
документированно отвечал `400`. Тест исправлен: перед вызовом он
регистрирует отдельный рантайм на подходящем провайдере и отдельного
агента на нём, не трогая общий рантайм/агента фикстуры.

## Итог

- Прогон контрактного набора против эталона (`BASE_URL=http://localhost:8199
  GOOSAR_DEV_VERIFICATION_CODE=424242 go test ./e2e/contract/... -v`):
  **0 FAIL**, покрытие **365/406** документированных операций
  (для операций вне покрытия при полном прогоне это ожидаемо — часть из них
  требует инфраструктуры, которую набор сознательно не поднимает, например
  реального OIDC/LDAP/бинарной сборки демона).
- `python3 e2e/contract/check_routes.py` — 0 расхождений
  (маршруты router.go и `docs/50-api-contract.yaml` совпадают: 406/406).
- Повторный прогон сразу после первого (без пауз, на том же поднятом
  эталоне) также даёт 0 FAIL — тесты идемпотентны. Один быстрый повтор
  подряд третий-четвёртый раз может упереться в лимит частоты на
  `/auth/send-code`, но это ограничение самого эталона на количество
  запросов кода за окно времени, не связанное с состоянием, которое
  оставляют тесты.
