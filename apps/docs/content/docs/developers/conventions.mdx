## 1. Именование в коде [#1-code-naming]

### Маршруты [#routes]

Маршруты до рабочего пространства (те, что доступны, пока пользователь ещё не внутри) обязаны быть либо одним словом, либо шаблоном `/{noun}/{verb}`.

- ✅ `/login`, `/inbox`, `/workspaces/new`
- ❌ `/new-workspace`, `/create-team`, `/accept-invite`

Словосочетания через дефис в корне конфликтуют со слагами рабочих пространств, которые выбирают пользователи, и заставляют бесконечно пересматривать список зарезервированных слагов. Резервирование существительного (`workspaces`) автоматически защищает всё поддерево `/workspaces/*`.

### Маршруты внутри рабочего пространства [#workspace-scoped-routes]

Всегда живут по шаблону `/{slug}/{section}` — `/{slug}/issues`, `/{slug}/agents`, `/{slug}/settings`. Логику маршрутизации рабочего пространства дублировать нельзя: в общем коде используйте `useNavigation().push()`, а не link-API конкретного фреймворка.

### Пакеты и модули [#packages-and-modules]

В монорепозитории границы пакетов жёсткие:

| Пакет | Может зависеть от | Не должен зависеть от |
| --- | --- | --- |
| `packages/core` | ничего специфичного для приложений | `react-dom`, `localStorage`, `process.env`, `next/*`, UI-библиотеки |
| `packages/ui` | ничего | `@goosar/core`, бизнес-логика |
| `packages/views` | `core/`, `ui/` | `next/*`, `react-router-dom`, stores |
| `apps/web/platform/` | `next/*` | другие приложения |
| `apps/desktop/.../platform/` | `react-router-dom`, electron | другие приложения |

Если логика появилась в обоих приложениях, её обязательно выносят в общий пакет. Исключений для «маленького» дублирования нет.

### Файлы и компоненты [#files-and-components]

- Файлы: `kebab-case.tsx` / `kebab-case.ts` (например, `agent-row-actions.tsx`)
- Компоненты: `PascalCase` (например, `AgentRowActions`)
- Хуки: `useCamelCase` (например, `useWorkspaceId`)
- Тесты: рядом с исходником, `<file>.test.ts(x)`
- Стор Zustand: `<feature>-store.ts`, экспорт `use<Feature>Store`

### База данных (Go + sqlc) [#database-go-sqlc]

- Таблицы: `snake_case` в единственном числе (`user`, `workspace`, `agent_runtime`)
- Колонки: `snake_case` (`workspace_id`, `created_at`, `last_seen_at`)
- Внешние ключи: `<table>_id`
- Булевы: `is_<state>` или `<state>_at` (для смены состояния предпочтителен вариант с меткой времени)
- Файлы миграций: `NNN_descriptive_name.up.sql` и `.down.sql` — всегда обе стороны

### Go [#go]

- Стандартные `gofmt` и `go vet`. Без исключений.
- Файлы handler повторяют домен: `agent.go`, `auth.go`, `runtime.go`
- Тесты: `<file>_test.go` рядом с исходником
- Разбор UUID в handler идёт по правилу из корневого `CLAUDE.md`: `parseUUIDOrBadRequest` для входа с границы, `parseUUID` (с panic) для доверенных круговых обходов, и никогда `util.ParseUUID` без проверки ошибки.

### TypeScript [#typescript]

- Ответы API по сети приходят в `snake_case`; api-клиент переводит их в `camelCase` на границе. Внутри кода на TS — **всегда camelCase**.
- Типы: `PascalCase` (`Issue`, `AgentRuntime`); без префикса `I`, без суффикса `_t`.
- Перечисления: предпочтительны юнионы строковых литералов; `enum` — только там, где значения нужно перебирать в рантайме.
- Ключи TanStack Query: фабричные функции в `<feature>/queries.ts`, например `issueKeys.detail(id)`.

### Отображаемые имена сред выполнения [#runtime-display-names]

`AgentRuntime.name` — сырое техническое имя от демона (например, `Runtime E (host)`), а пользовательский алиас лежит в `custom_name`. В видимых пользователю текстах `runtime.name` рендерить нельзя: используйте общие хелперы, чтобы алиас и провайдер оставались согласованными:

- Самостоятельная подпись среды выполнения (списки, чипы, диалоги подтверждения, заголовки окон): `runtimeDisplayLabel(runtime)` — алиас плюс провайдер, с откатом на имя от демона.
- Когда рядом уже стоит иконка или текст провайдера: `runtimeDisplayName(runtime)` — только алиас, без повторения провайдера.
- Внутри группы по машине: заголовок машины использует `machine.title`, дочерние строки — `runtimeRowLabel(runtime, machine.title)`.
- Селекторы сред выполнения группируются по машинам через `buildRuntimeMachines`; плоский список сырых имён собирать не нужно.

Сырое `runtime.name` допустимо только для внутренней идентификации — разбора имени хоста, группировки, поисковых индексов и полезной нагрузки протокола — и никогда для текста в JSX, параметров i18n, подписей `<Select>` и заголовков окон.

### Ключи issue [#key-format]

У каждого issue есть человекочитаемый ключ вида `ABC-123`: `issue_prefix` рабочего пространства (заглавные буквы и цифры, обычно 3 символа, максимум 10) плюс порядковый номер. Админ рабочего пространства может изменить префикс в Settings → General; при изменении перенумеровываются все существующие issue, поэтому внешние ссылки со старым префиксом — заголовки PR, имена веток, ссылки в документации и чатах — перестают разрешаться.

### Комментарии в коде [#comments-in-code]

Только английский. Правило действует и для Go, и для TypeScript. Комментарий на русском или китайском в коде — это баг, его надо заменить.

### Сообщения коммитов [#commit-messages]

Conventional-формат: `feat(scope)`, `fix(scope)`, `refactor(scope)`, `docs`, `test(scope)`, `chore(scope)`. Коммиты атомарные, сгруппированные по замыслу.

## 2. Глоссарий перевода i18n [#2-i18n-translation-glossary]

Это **обязательный** глоссарий для каждого PR с переводом. Раньше он жил в `packages/views/locales/glossary.md`; теперь тот файл — заглушка со ссылкой сюда.

Русская локаль — язык продукта по умолчанию, поэтому эталон здесь один: русские строки в `packages/views/locales/ru/*.json`. Названия разделов, кнопок и сущностей в документации берутся из локали дословно — читатель ищет в интерфейсе ровно то слово, которое прочитал на странице. Если для термина не находится строки в локали, ориентир — уже написанные страницы `apps/docs/content/docs/*.mdx`.

### Ключевое различие: сущность и понятие [#the-core-distinction-entity-vs-concept]

Продуктовые существительные Goosar делятся на две категории:

- **Сущность** — у неё есть URL, строка в базе данных, тип в API. В русском тексте пишется **латиницей и не склоняется**, чтобы визуально читалась как имя типа и говорила: «это конкретная сущность системы Goosar».
- **Понятие** — обычное существительное, а не сущность в базе. **Переводится полностью**, чтобы читатель не спотыкался об английские вставки.

### Сущности — латиницей и без склонения [#entities-latin-and-indeclinable]

`issue`, `skill`, `task` — основные сущности Goosar. У них английские колонки схемы, поля API и подписи в интерфейсе. В русском тексте действует смешанное правило: как писать слово, зависит от того, где оно стоит.

| Контекст | Как писать | Пример |
| --- | --- | --- |
| **Строки интерфейса, названия состояний, ссылки на код** | латиницей, строчными | «issue в очереди», «создать дочерний issue», «прикрепить skill агенту» |
| **Заголовки страниц и разделов документации** | латиницей с заглавной **или** русский термин | «Issue и проекты», «Skills», «Задачи» |
| **Длинная проза, где сущность — подлежащее** | русский термин, при первом появлении английский в скобках | «**Задача** (task) — единица каждого запуска агента» |
| **Поля API и БД** | всегда `task` / `issue` / `skill` | `task_id`, `issue_status`, `skill_uuid` |

Соответствия:

- `issue` ↔ **issue**. Устоявшегося русского перевода нет: «задача» уже занята под `task`, «тикет» — из мира сервис-деска, «обращение» — из поддержки. Слово не склоняется: «два issue», «в этом issue», «список issue».
- `task` ↔ **задача**. Речь всегда о запуске агента, а не о работе человека.
- `skill` ↔ **skill**. Как и `issue`, пишется латиницей и не склоняется; множественное число — `skills`, как в локали и в заголовке страницы «Skills»: «несколько skills», «каталог skills», «содержимое skill».

**Почему `project` и `autopilot` переводятся, а `issue` — нет**: «проект» и «автопилот» — обычные русские слова, они не создают двусмысленности. У `issue` русского эквивалента, который не пересекался бы с «задачей», нет.

### Роли и состояния (латиницей, не переводятся) [#roles-and-states]

Это идентификаторы уровня схемы, в русском тексте они остаются латиницей:

- Роли: `owner` / `admin` / `member`
- Статусы issue: `backlog` / `todo` / `in_progress` / `in_review` / `done` / `blocked` / `cancelled`

В интерфейсе для этих значений допустимы русские подписи (`Бэклог`, `В работе`, `Готово`), но в прозе документации, где речь о значении поля, пишется латиница в code-стиле: «статус переходит в `in_progress`».

### Множественное число и счётчики [#plurals-and-counts]

В i18next русский язык требует все четыре формы: `_one`, `_few`, `_many`, `_other`. Пропущенная форма приводит к «5 задача» в интерфейсе.

```json
// en/issues.json
{
  "issue_count_one": "{{count}} issue",
  "issue_count_other": "{{count}} issues"
}

// ru/issues.json
{
  "issue_count_one": "{{count}} issue",
  "issue_count_few": "{{count}} issue",
  "issue_count_many": "{{count}} issue",
  "issue_count_other": "{{count}} issue"
}
```

Несклоняемые сущности (`issue`) одинаковы во всех формах, склоняемые слова различаются:

- `{{count}} agents` → `{{count}} агент` / `агента` / `агентов` / `агента`
- `{{count}} comments` → `{{count}} комментарий` / `комментария` / `комментариев` / `комментария`
- `{{count}} members` → `{{count}} участник` / `участника` / `участников` / `участника`

### Подстановки [#interpolation]

Форма `{{var}}`. В русском переводе порядок слов можно менять под естественную грамматику.

```json
// en
{ "welcome_message": "Welcome back, {{name}}!" }

// ru
{ "welcome_message": "С возвращением, {{name}}!" }
```

### Именование ключей [#key-naming]

Три уровня вложенности: `feature.component.action`.

```json
{
  "feature_or_component": {
    "subcomponent_or_section": {
      "action_or_label": "..."
    }
  }
}
```

Примеры:

- `issues.toolbar.batch_update_success`
- `issues.detail.comment_form.placeholder`
- `inbox.empty.title`
- `settings.preferences.language.title`

### Где живут тексты только для веба и только для десктопа [#web-only-desktop-only-copy]

- Общий текст: верхний уровень JSON пространства имён
- Только веб: секция `web`
- Только десктоп: секция `desktop`

Образец — `auth.json` (секция `web` содержит `prefer_desktop` и `desktop_handoff.*`).

## 3. Русский стиль [#3-russian-voice]

### Пунктуация и типографика [#punctuation]

- Кавычки: «ёлочки» в прозе интерфейса и документации. Внутренние — „лапки“, но вложенность лучше переписать.
- Тире: длинное тире «—» с пробелами. Дефис только внутри слов (`MCP-сервер`).
- Буква «ё» пишется там, где она есть в слове: «всё», «её», «объём».
- Многоточие: три точки `...`, как в английском исходнике, а не символ `…`.
- Термины латиницей окружаются обычными пробелами: «создать issue», «настроить skill».

### Принципы [#style-principles]

- **Просто и прямо.** Без канцелярита («осуществляется», «в целях», «является»), без переводческих калек («для того чтобы», «в качестве»).
- **Обращение на «вы» со строчной буквы.** «Откройте настройки», «вы увидите».
- **Сообщения об ошибках** — спокойные и конкретные: «Не удалось сохранить изменения» лучше, чем «Ошибка сохранения!».
- **Кнопки** — глагол в инфинитиве или повелительном наклонении, 1–3 слова: «Сохранить», «Отмена», «Синхронизировать сейчас».
- **Подсказки (tooltip)** — законченная короткая фраза: «Скопировать ссылку в буфер обмена».
- **Placeholder** — пример, а не команда: «Заголовок issue...».
- Никаких маркетинговых усилителей («мощный», «легко и просто», «революционный») и эмодзи в продуктовом тексте.

### Куда смотреть, если слова нет в глоссарии [#where-to-look]

Порядок проверки:

1. `packages/views/locales/ru/` — строки продукта, в первую очередь `layout.json` (названия разделов), `issues.json`, `runtimes.json`, `settings.json`
2. `apps/docs/content/docs/*.mdx` — как термин уже звучит в связном тексте
3. `packages/views/locales/ru/auth.json` — образец структуры JSON и использования selector API
4. `packages/views/settings/components/preferences-tab.tsx` — переключатель языка

## Когда правите эту страницу [#when-you-change-this-page]

Вместе с правкой правил нужно:

1. Раскатать правило по соответствующим JSON локалей, `CLAUDE.md` и страницам документации
2. Написать в описании PR, что именно изменилось, чтобы ревьюер проверил, подтянуты ли зависимые места

Эта страница — контракт; другие документы её не переопределяют.
