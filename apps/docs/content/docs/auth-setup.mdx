Goosar по умолчанию пускает пользователей по **почте и коду подтверждения**. После успешного входа сервер выдаёт cookie с JWT; срок жизни по умолчанию — 30 дней и задаётся переменной `AUTH_TOKEN_TTL`. На этой странице описано, как настроить доставку писем, кто может зарегистрироваться и как подключить корпоративный вход.

Все переменные окружения, упомянутые ниже, перечислены с комментариями в `.env.example` в корне репозитория. О том, как устроены токены, см. [Аутентификация и токены](/auth-tokens); о развёртывании — [Быстрый старт для самостоятельного размещения](/self-host-quickstart).

## Как работает вход по почте и коду [#how-email-code-sign-in-works]

Пользователь вводит почту на странице входа, сервер отправляет 6-значный код, пользователь вводит его, сервер проверяет код и выдаёт cookie с JWT. Для отправки писем поддерживаются два варианта.

### Вариант A: Resend [#option-a-resend]

Подходит для облачных развёртываний с выходом в интернет.

1. Создайте аккаунт [Resend](https://resend.com/) и подтвердите домен отправителя.
2. Создайте API-ключ.
3. Задайте переменные окружения:

    ```bash
    RESEND_API_KEY=re_xxxxxxxxxxxxxxxx
    RESEND_FROM_EMAIL=noreply@example.local  # домен должен быть подтверждён в Resend
    ```

4. Перезапустите сервер.

### Вариант B: SMTP-релей [#option-b-smtp-relay]

Подходит для самостоятельного размещения и закрытых контуров: когда сервер не может обратиться к `api.resend.com` или у вас уже есть внутренний почтовый релей (Microsoft Exchange, Postfix и т. п.). Если задан `SMTP_HOST`, сервер всегда отправляет письма через SMTP, даже при заданном `RESEND_API_KEY`, поэтому письма с кодами и приглашениями не покидают внутреннюю сеть.

Адрес отправителя берётся из `SMTP_FROM_EMAIL`; если он не задан, используется `RESEND_FROM_EMAIL`. Если не задан ни один из них, сервер не запустится.

Поддерживаются три режима релея:

| Режим | Порт | Авторизация | TLS |
|---|---|---|---|
| Анонимный внутренний релей | `25` | нет: отправка разрешена по IP или подсети | нет на линии (только во внутреннем сегменте) |
| Авторизованная отправка | `587` | `SMTP_USERNAME` и `SMTP_PASSWORD` | STARTTLS, включается автоматически |
| Неявный TLS (SMTPS) | `465` | необязательна (`SMTP_USERNAME` и `SMTP_PASSWORD`) | TLS-рукопожатие при подключении; включается автоматически на порту `465`, на другом порту — через `SMTP_TLS=implicit` |

**Анонимный релей на порту 25** — типичный внутренний релей или анонимный приёмный коннектор Exchange, который принимает почту из доверенной подсети без учётных данных:

```bash
SMTP_HOST=mail.example.local
SMTP_PORT=25
SMTP_USERNAME=
SMTP_PASSWORD=
SMTP_TLS_INSECURE=false
SMTP_FROM_EMAIL=noreply@example.local
```

**Авторизованная отправка на порту 587** — для релеев, которым нужна служебная учётная запись. STARTTLS включается автоматически, если сервер его предлагает:

```bash
SMTP_HOST=smtp.example.local
SMTP_PORT=587
SMTP_USERNAME=goosar
SMTP_PASSWORD=...
SMTP_TLS_INSECURE=false        # true только для самоподписанного сертификата или частного CA
SMTP_FROM_EMAIL=noreply@example.local
```

**Неявный TLS (SMTPS) на порту 465** — для провайдеров, которые предлагают только SMTPS и не объявляют STARTTLS. На порту `465` неявный TLS включается автоматически; на нестандартном порту SMTPS его включает `SMTP_TLS=implicit` (синонимы: `smtps`, `ssl`):

```bash
SMTP_HOST=smtp.example.local
SMTP_PORT=465                  # неявный TLS включается автоматически на 465
SMTP_USERNAME=goosar@example.local
SMTP_PASSWORD=...
SMTP_TLS=implicit              # на 465 необязательно, на нестандартном порту SMTPS обязательно
SMTP_FROM_EMAIL=noreply@example.local
```

**Строгие публичные релеи** (например, Google Workspace `smtp-relay.gmail.com`) дополнительно требуют корректное имя в EHLO. Приветствие `localhost` с публичного адреса они отклоняют и обрывают соединение, а это проявляется как невнятный `EOF` на одной из следующих команд (`smtp auth: EOF`), а не на самом приветствии. Задайте в `SMTP_EHLO_NAME` FQDN, который ждёт релей. По умолчанию берётся имя хоста, а внутри контейнера оно обычно не является корректным FQDN:

```bash
SMTP_HOST=smtp-relay.example.local
SMTP_PORT=587
SMTP_EHLO_NAME=mail.example.local   # FQDN, который принимает релей
SMTP_FROM_EMAIL=noreply@example.local
```

При старте сервер пишет в лог, какой способ отправки выбран, включая режим TLS, например `EmailService: SMTP relay mail.example.local:25 (starttls) from=noreply@example.local`. Пароль в лог не попадает. Если после перезапуска такой строки нет, значит `SMTP_HOST` не дошёл до процесса: проверьте окружение контейнера (`docker compose -f docker-compose.selfhost.yml exec backend env | grep SMTP`).

<Callout type="warning">
**Что будет, если не настроен ни один способ отправки.** При `APP_ENV=production` (а также при `GOOSAR_DELIVERY_PROFILE=perimeter`) сервер отказывает во входе с ответом 503 и кодом `email_not_configured`, а не печатает код в лог, который пользователь не прочитает. Вне production коды выводятся в лог сервера: это удобно для локальной разработки.
</Callout>

## Фиксированный код для локальной разработки [#fixed-local-testing-codes]

<Callout type="warning">
**Не включайте фиксированный код подтверждения на инстансе, доступном из сети.**

По умолчанию фиксированного кода нет: `888888` и любые другие значения воспринимаются как обычный неверный код, пока вы явно не настроите обратное.

Для локальной разработки без почтового бэкенда (без Resend и без SMTP) используйте сгенерированный код из лога сервера. Если нужна детерминированная автоматизация в локальной или закрытой среде, задайте `GOOSAR_DEV_VERIFICATION_CODE` шестизначным значением, например `888888`, и оставьте `APP_ENV` не production:

```bash
APP_ENV=development
GOOSAR_DEV_VERIFICATION_CODE=888888
```

При `APP_ENV=production` эта переменная игнорируется.
</Callout>

В production оставляйте `GOOSAR_DEV_VERIFICATION_CODE` пустой и задайте `APP_ENV=production`. При развёртывании через `make selfhost` и `docker-compose.selfhost.yml` по умолчанию используется `APP_ENV=production`.

## Корпоративный вход: OIDC и LDAP [#corporate-sign-in]

Кроме входа по почте, сервер поддерживает вход через OIDC и LDAP/Active Directory. Какие методы предлагает развёртывание, определяет `GOOSAR_AUTH_METHODS` — список через запятую из `email`, `oidc`, `ldap`. Если переменная пуста, доступен только `email`, поэтому обновление существующего стенда ничего не меняет. Метод, которого нет в списке, закрыт на уровне сервера, даже если он настроен.

- **OIDC** (основной корпоративный способ). Работает с любым провайдером, который отдаёт `/.well-known/openid-configuration` и JWKS: Keycloak, ADFS, Okta, Authentik, Yandex ID и др. Используется Authorization Code с PKCE. Задайте `GOOSAR_OIDC_ISSUER` (только HTTPS, без суффикса `/.well-known/openid-configuration`), `GOOSAR_OIDC_CLIENT_ID`, при необходимости `GOOSAR_OIDC_CLIENT_SECRET` (пустое значение — публичный клиент) и `GOOSAR_OIDC_REDIRECT_URL`, который должен точно совпадать с адресом, зарегистрированным у провайдера, например `https://goosar.example.local/api/auth/oidc/callback`.
- **LDAP/AD** (запасной путь, когда IdP нет). Форма «логин и пароль». Адрес каталога задаётся в `GOOSAR_LDAP_URL`: `ldaps://` либо `ldap://` вместе с `GOOSAR_LDAP_START_TLS=true`. Открытый `ldap://` без StartTLS сервер отклоняет, потому что иначе доменный пароль ушёл бы по сети открытым текстом. Для поиска пользователя нужны `GOOSAR_LDAP_BIND_DN`, `GOOSAR_LDAP_BIND_PASSWORD` и `GOOSAR_LDAP_BASE_DN`.

При первом входе через IdP или каталог учётная запись создаётся автоматически; для нового пользователя действуют те же списки допустимых адресов, что и для входа по почте (см. ниже). Если в OIDC `email_verified=false`, вход в уже существующую учётную запись по такому адресу отклоняется. Права администратора развёртывания по группе каталога не выдаются молча: сервер заводит ожидающую заявку, которую подтверждает оператор командой `goosar_admin confirm <id>`. Полный список переменных и их описание — в `.env.example`, обоснование решений — в `docs/auth/corporate-auth.md`.

## Ограничение регистрации [#restricting-who-can-sign-up]

Регистрацию ограничивают три переменные окружения; они применяются в порядке приоритета:

<Mermaid chart={`
graph TD
    Start[Первый вход нового пользователя] --> A{Почта в<br/>ALLOWED_EMAILS?}
    A -- Да --> Allow[Разрешить регистрацию]
    A -- Нет --> B{Домен в<br/>ALLOWED_EMAIL_DOMAINS?}
    B -- Да --> Allow
    B -- Нет --> C{Заполнен ли<br/>хотя бы один список?}
    C -- Да --> Block[Отклонить]
    C -- Нет --> D{ALLOW_SIGNUP<br/>= true?}
    D -- Да --> Allow
    D -- Нет --> Block
`} />

**Уже зарегистрированные пользователи могут входить всегда**: списки действуют только при **первой регистрации**.

- **`ALLOWED_EMAILS`** (высший приоритет) — явный список адресов через запятую. **Если он не пуст, зарегистрироваться могут только перечисленные адреса.**
- **`ALLOWED_EMAIL_DOMAINS`** — список доменов через запятую, например `company.example,partner.example`.
- **`ALLOW_SIGNUP`** — общий выключатель, по умолчанию `true`. Значение `false` полностью отключает регистрацию.

<Callout type="warning">
**Уровни работают по логике «И», а не «ИЛИ».** Частая ошибка — считать, что `ALLOWED_EMAIL_DOMAINS=company.example` вместе с `ALLOW_SIGNUP=true` означает «пустить сотрудников `company.example` и всех остальных». Это не так. Если хотя бы один список не пуст, адреса, которые ему не соответствуют, **отклоняются сразу**, и `ALLOW_SIGNUP=true` этого не отменяет.

Чтобы разрешить регистрацию всем, оставьте все три переменные пустыми (или только `ALLOW_SIGNUP=true`).
</Callout>

Типичные конфигурации:

| Цель | Настройка |
|---|---|
| Только внутренние сотрудники `company.example` | `ALLOWED_EMAIL_DOMAINS=company.example` |
| Сотрудники и несколько внешних участников | `ALLOWED_EMAIL_DOMAINS=company.example`, адреса внешних участников в `ALLOWED_EMAILS` |
| Самостоятельная регистрация отключена, только по приглашениям | `ALLOW_SIGNUP=false` |
| Открытая регистрация (для production не рекомендуется) | все три переменные пусты |

Изменение этих переменных применяется после перезапуска бэкенда, без пересборки веб-части.

## Можно ли приглашать, если регистрация закрыта [#can-you-invite-when-signup-is-disabled]

**Только тех, у кого уже есть аккаунт Goosar.** При принятии приглашения списки допустимых адресов не проверяются: если приглашённый уже зарегистрирован (например, в другом рабочем пространстве), он может перейти по ссылке, войти и принять приглашение.

**Тех, кто ни разу не регистрировался, приглашение не спасёт.** Чтобы принять его, нужно сначала войти, а первый шаг входа (запрос кода) проходит проверку списков. При `ALLOW_SIGNUP=false` или если адрес не входит в `ALLOWED_EMAILS` и `ALLOWED_EMAIL_DOMAINS`, человек **не сможет зарегистрироваться**, а значит, и принять приглашение.

Чтобы пригласить внешнего участника, который ещё не зарегистрирован, временно добавьте его адрес в `ALLOWED_EMAILS`, дождитесь, пока он зарегистрируется и примет приглашение, и уберите запись.
